# Abstract

This document specifies a minimal GitHub configuration bundled with the kubernetes and machine Charmcraft profiles. The configuration lives inside a `.github/` directory generated by the Charmcraft commands:

* `charmcraft init --profile machine` and  
* `charmcraft init --profile kubernetes`

We skip the 12-factor profiles, because Platform Engineering doesn’t have plans to include any CI configuration. GitHub configuration is too specific for the 12-factors, and shipping multiple different CI (Jenkins, Gitlab, or Bitbucket) configs is not desirable.

This configuration includes recommendations from Charm Tech on what Charms should run in CI if they host their git repository on GitHub. There are two ways Charmers can consume this configuration:

* They receive it when initialising their Charm with Charmcraft  
* For existing charms, we suggest they initialise a simple Charm and bring over the config. They can also use `charmcraft init --force`, but Charm Tech doesn’t recommend it.

As the config lives inside a single `.github` directory, Charmers can easily opt out by removing or ignoring it.

# Rationale

Charmers initialise their charm with `charmcraft init`. This command currently doesn’t generate any GitHub configuration, and GitHub is likely to be where the charm source is hosted. New Charmers who want to set up their own CI have some options:

* Follow [How to set up continuous integration for a charm](https://canonical.com/juju/docs/ops/latest/howto/set-up-continuous-integration-for-a-charm/). Charmers need to build and test CI by themselves. This page’s scope doesn’t cover Dependabot or other security scanning workflows.  
* Use available workflows for charm CI: [craft-actions](https://github.com/canonical/craft-actions), [operator-workflows](https://github.com/canonical/operator-workflows), [charming-actions](https://github.com/canonical/charming-actions/), and [charm-ci](https://github.com/canonical/charm-ci). Each has a different level of maturity and use cases.  
* Copy the setup from another charm. But charms from other teams have their own setup. For example, the [Observability team reusable workflows](https://github.com/canonical/observability/tree/main/.github/workflows). This is not something we recommend for new Charmers.

We recommend [How to set up continuous integration for a charm](https://canonical.com/juju/docs/ops/latest/howto/set-up-continuous-integration-for-a-charm/) for new charms, and Charmers will need to set up the CI themselves. This leads to higher chances of drifting away from best practices. Therefore, a default GitHub configuration that Charmers can use straightaway speeds up their CI setup while maintaining best practices.

## Goals

* The configuration is shipped in a single `.github/` directory for each of the `machine` and `kubernetes` profiles.  
* Tools used in the workflows, if possible, should be versioned in `pyproject.toml`  
* The configuration includes:  
  * Software quality: linting, unit tests, and integration tests  
  * Dependabot config  
  * Security workflows: `zizmor`, `pip-audit` , and [dependency-review](https://github.com/canonical/charm-ubuntu/blob/master/.github/workflows/dependency-review.yaml)  
  * `SECURITY.md`  
  * Publishing workflow: publish the charm to edge on merge to the default branch  
* All external GHA workflow calls must be pinned to its SHA, using the following format

```
- name: Boo
  uses: <action-name>@<sha>  # <version_number>
```

### **Non functional requirements:**

* For CI tools that can be versioned in `pyproject.toml`, we set the lower bound to the latest `<major>.<minor>` version, and lower than the next major version (for example, `>=1.5,<2`). Charm Tech plans to update the versions in `pyproject.toml` once per cycle for regular updates. Security bumps will land on Charmcraft’s `hotfix/*` branches and be released as soon as possible.    
* The configuration is applicable for both Canonical and external Charmers. This means we don’t include Canonical-specific workflows (for example: TIOBE).   
* We focus on public GitHub repositories, and use features that are available there. Charmers should be careful when using this config for private repositories, as some features require [GitHub Advanced Security](https://docs.github.com/en/get-started/learning-about-github/about-github-advanced-security). See [Requirements for private repositories](#requirements-for-private-repositories) for more information.  
* All workflow files must have:  
  * `.yaml` extension  
  * 2-space indentation

## Out of scope

* Documentation build workflows  
* SBOM generation

# Specification

## Layout

The layout of `.github` is similar between the machine and k8s profiles. The content of each file might be different:

```
.github/
    dependabot.yaml
    workflows/
        ci.yaml
        security.yaml
        zizmor.yaml
        dependency-review.yaml
        integration.yaml
        publish.yaml
```

`SECURITY.md` is added in the root of the profile, and `pyproject.toml` receives a new dependency group and pytest log configs.

## pyproject.toml

We define a new dependency group `ci` for CI’s specific tools.

```
[dependency-groups]
...
ci = [
    "pip-audit>=2.10,<3",
    "tox>=4.64,<5",
    "tox-uv>=1.36,<2",
    "zizmor>=1.30,<2",
]
```

And configure Jubilant [log to a file](https://canonical.com/juju/docs/ops/latest/howto/write-integration-tests-for-a-charm/#log-to-a-file):

```
[tool.pytest.ini_options]
...

# Retain INFO logs in the "Captured log call" section when run interactively.
# Otherwise, that section will have DEBUG logs (coming from log_file_level).
log_level = "INFO"

log_cli_format = "%(levelname)s %(name)s %(message)s"

log_file_level = "DEBUG"
log_file_format = "%(asctime)s %(levelname)s %(name)s %(message)s"
log_file_date_format = "%Y-%m-%dT%H:%M:%SZ"
```

## .github/workflows/integration.yaml

This workflow runs the Jubilant integration tests of the Charm. It follows Charm Tech recommendation [set-up-continuous-integration-for-a-charm](https://canonical.com/juju/docs/ops/latest/howto/set-up-continuous-integration-for-a-charm/):

* `concierge` provisions Juju and the substrate  
* `tox -e integration` runs integration tests that are already in the profile. It stores pytest’s log file (specified by the `--log-file` argument) to the same directory as pytest-jubilant’s `juju debug-log`

This workflow is run by `workflow_call` from `.github/workflows/ci.yaml`. It will only run when unit tests and linting pass, preventing resource-consuming integration test runs. This workflow should be configured as a required status check in branch protection, so a PR cannot merge unless lint, unit, and all matrix integration checks pass.

For `init-kubernetes` profile:

```
name: Integration Tests

on:
  workflow_call:
  workflow_dispatch:

permissions: {}

jobs:
  integration:
    name: Integration tests
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        juju-version: ["3.6", "4.0"]
    concurrency:
      group: ${{ github.workflow }}-${{ github.ref }}-${{ matrix.juju-version }}
      cancel-in-progress: true
    steps:
      - name: Checkout
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false

      - name: Set up uv
        uses: astral-sh/setup-uv@c18668ad3cf93ea998bef934396af7bb5c839dc7  # v10.2.0

      - name: Set up tools to run the integration tests
        run: uv sync --frozen --only-group ci

      - name: Set up Concierge
        run: sudo snap install --classic concierge

      - name: Set up Juju and charm development tools
        run: sudo concierge prepare -p k8s --juju-channel ${{ matrix.juju-version }}/stable

      - name: Pack the charm
        # The integration tests don't pack the charm. Instead, they look for a .charm
        # file in the project dir (or use CHARM_PATH, if set).
        run: charmcraft pack

      - name: Run integration tests
        timeout-minutes: 60
        run: uv run --frozen tox -e integration -- --juju-dump-logs logs --log-file logs/verbose.log

      - name: Upload logs
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a  # v7.0.1
        with:
          name: integration-test-logs-juju-${{ matrix.juju-version }}
          path: logs
```

The `init-machine` profile is identical except for the `concierge` preset:

```
      - name: Set up Juju and charm development tools
        run: sudo concierge prepare -p machine --juju-channel ${{ matrix.juju-version }}/stable
```

## .github/workflows/ci.yaml

This workflow defines the lint and unit tests across the Python version that the Charm supports. This is the system Python version of the base. 

At the moment, we have 24.04 base for both kubernetes and machine profiles, so Python 3.12 is selected.

```
name: Check
on:
  push:
    branches:
      - main
  pull_request:

permissions: {}

jobs:
  lint:
    name: Lint
    runs-on: ubuntu-latest
    container:
      image: python:3.12
    steps:
      - name: Check out code
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false

      - name: Install uv
        uses: astral-sh/setup-uv@c18668ad3cf93ea998bef934396af7bb5c839dc7  # v10.2.0

      - name: Run lint
        run: uv run --frozen --only-group ci tox -e lint

  unit:
    name: Unit Tests
    runs-on: ubuntu-latest
    container:
      image: python:3.12
    steps:
      - name: Check out code
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false

      - name: Install uv
        uses: astral-sh/setup-uv@c18668ad3cf93ea998bef934396af7bb5c839dc7  # v10.2.0

      - name: Run tests
        run: uv run --frozen --only-group ci tox -e unit

  integration:
    name: Integration Tests
    needs: [lint, unit]
    uses: $/.github/workflows/integration.yaml
```

## .github/workflows/publish.yaml

This is a simple workflow for publishing the charm to `latest/edge` on CharmHub, for every push to main. This is a good starting point for new Charmers.

The workflow requires a `CHARMHUB_TOKEN` secret that stores the [Charmhub token](https://canonical.com/juju/docs/charmcraft/latest/howto/manage-the-current-charmhub-user/#remote-environments). This token is used by Charmcraft to upload and release the Charm to Charmhub. Charmers  should set up an [environment](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments#creating-an-environment), and create a `CHARMHUB_TOKEN` secret that belongs in it.

```
name: Publish to edge

on:
  push:
    branches:
      - "main"

permissions: {}

jobs:
  publish-edge:
    name: Publish to latest/edge
    runs-on: ubuntu-latest
    environment: publish
    steps:
      - name: Checkout repository
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false

     -  name: Set up LXD
        uses: canonical/setup-lxd@8c6a87bfb56aa48f3fb9b830baa18562d8bfd4ee  # v1
        with:
          channel: 5.21/stable

      - name: Install charmcraft
        run: sudo snap install --classic charmcraft

      - name: Pack the charm
        run: charmcraft pack

      - name: Upload charm to latest/edge
        run: |
          for charm in *.charm; do
            charmcraft upload "$charm" --release latest/edge
          done
        env:
          CHARMCRAFT_AUTH: ${{ secrets.CHARMHUB_TOKEN }}
```

## .github/dependabot.yaml

This file contains the recommended Dependabot config for the Charm repo. It follows Charm Tech convention [OP0xx-dependabot-config-conventions](https://github.com/canonical/charm-tech/blob/main/specs/OP0xx-dependabot-config-conventions.md), where dependencies are grouped into separate PRs for easier review. Charmers need to enable [Dependabot](https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/dependabot-quickstart#enabling-dependabot-for-your-repository) alerts, security updates, and version updates.

```
version: 2

updates:
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "monthly"
    labels:
      - "dependencies"
    open-pull-requests-limit: 100
    cooldown:
      default-days: 7
      semver-major-days: 14
    groups:
      actions:
        patterns:
          - "*"

  - package-ecosystem: "uv"
    directory: "/"
    schedule:
      interval: "monthly"
    labels:
      - "dependencies"
    open-pull-requests-limit: 100
    cooldown:
      default-days: 7
      semver-major-days: 14
    groups:
      # Canonical's packages (we trust the release).
      canonical:
        patterns:
          - "charmlibs-*"
          - "jubilant"
          - "ops"
          - "ops-scenario"
          - "ops-tracing"
          - "pytest-jubilant"
      # Linters / type-checkers / formatters. Majors ride along; we do not
      # pin these and a major ruff/pyright is low-risk to review in a batch.
      dev-tooling:
        patterns:
          - "ruff"
          - "pyright"
          - "codespell"
          - "coverage"
      # Test runner + other shared test deps.
      test-deps:
        patterns:
          - "pytest"
          - "pytest-*"
      # Everything else, minor + patch only. A runtime major falls through
      # to its own ungrouped PR so it never silently rides a patch bundle.
      runtime:
        patterns:
          - "*"
        update-types:
          - "minor"
          - "patch"
```

## .github/workflows/security.yaml

This workflow runs `pip-audit` to scan dependencies of the Charm for vulnerabilities. The scanning performs two steps:

* Freeze the dependencies information into a `requirements.txt` ignoring the Charm python project.  
* Install and run `pip-audit` on that `requirements.txt`

```
name: Dependency vulnerability scan

on:
  push:
    branches: ["main"]
  pull_request:

permissions: {}

jobs:
  pip-audit:
    name: pip-audit
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - name: Checkout repository
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false

      - name: Install uv
        uses: astral-sh/setup-uv@c18668ad3cf93ea998bef934396af7bb5c839dc7  # v10.2.0

      - name: Export locked dependencies (excluding this project)
        run: uv export --frozen --no-emit-project --no-hashes --format requirements-txt -o requirements.txt

      - name: Run pip-audit
        run: uv run --frozen --only-group ci pip-audit -r requirements.txt
```

## .github/workflows/zizmor.yaml

[zizmor](https://docs.zizmor.sh/) is a static analysis tool that can detect security issues in GitHub Actions workflows, and Dependabot config. This workflow will run zizmor and upload the result in SARIF format. This means the workflow will never fail ([reference](https://docs.zizmor.sh/integrations/#manual-integration)). We suggest adding a ruleset to prevent merging if there are serious issues detected by zizmor.

```
name: Workflow static checks

on:
  push:
    branches: ["main"]
  pull_request:
    branches: ["**"]

permissions: {}

jobs:
  zizmor:
    name: zizmor
    runs-on: ubuntu-latest
    permissions:
      security-events: write
    steps:
      - name: Checkout repository
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false

      - name: Install uv
        uses: astral-sh/setup-uv@c18668ad3cf93ea998bef934396af7bb5c839dc7  # v10.2.0

      - name: Run zizmor
        run: uv run --frozen --only-group ci zizmor --format=sarif . > results.sarif
        env:
          # We pass GH_TOKEN to enable zizmor's online mode. Online mode offers
          # more useful audits like checking for known vulnerable actions.
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

      - name: Upload SARIF file
        uses: github/codeql-action/upload-sarif@2892aa5e19bbd11bc0cff5427e3b750a04d9e3c2  # v4.38.2
        with:
          sarif_file: results.sarif
          category: zizmor
```

## .github/workflows/dependency-review.yaml

Dependency changes introduced by PRs can bring in vulnerabilities. This workflow scans PRs for such issues and fails if it finds high severity problems. It only runs on `pull_request`.   
 

```
name: Dependency review

on:
  pull_request:

permissions: {}

jobs:
  dependency-review:
    name: dependency-review
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - name: Checkout repository
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
        with:
          persist-credentials: false

      - name: Dependency review
        uses: actions/dependency-review-action@a1d282b36b6f3519aa1f3fc636f609c47dddb294  # v5.0.0
        with:
          fail-on-severity: high
```

## SECURITY.md

The `SECURITY.md` file points people to the GitHub security reporting feature as a starting point. This is a requirement for charm public listing. `SECURITY.md` mentions [GitHub’s security advisory](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository). This is disabled by default, and should be enabled to allow contributors privately reporting a security vulnerability.

Canonical charms can add in extra details following the company policy.

```
# Security policy

## Supported versions

TBD

## Reporting a vulnerability

Please provide a description of the issue, the steps you took to create the issue, affected versions, and, if known, mitigations for the issue.

The preferred way to report a security issue is through GitHub's security advisory for this project. See [Privately reporting a security
vulnerability](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing/privately-reporting-a-security-vulnerability) for instructions on reporting using GitHub's security advisory feature.
```

# Further Information

## Requirements for private repositories {#requirements-for-private-repositories}

Require GitHub Advanced Security (GHAS) in private repositories:

* `zizmor.yaml`'s `upload-sarif` step ([reference](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/integrate-with-existing-tools/upload-sarif-file))  
* [`actions/dependency-review-action`](https://github.com/actions/dependency-review-action) in `dependency-review.yaml`

## Decisions

* Daily sync Sep 28: this spec will not include [spread](https://github.com/canonical/spread). The final form of `charmcraft test` is not yet clear, it’s not clear how this would interact with the existing `test-machine` and `test-kubernetes` requirements, and we want to keep the profiles showing the simpler ways to do things as much as possible. We expect to update the profiles when the `charmcraft test` (and how that involves spread) story is clearer  
* An internal discussions: this spec will not include PR or Issue templates in the GitHub profiles  
  * They are opinionated in the area that we don’t want  
  * We are planning to add a CONTRIBUTING.md to the profiles (see [https://github.com/canonical/operator/issues/2771](https://github.com/canonical/operator/issues/2771)) which could mention that we recommend adding issue/PR templates  
* In review comments: we don’t include the workflow for validating PR title with conventional commit format (e.g. [charm-ubuntu](https://github.com/canonical/charm-ubuntu/blob/master/.github/workflows/validate-pr-title.yaml))  
  * Also too opinionated  
  * The workflow depends on a Python script for the validation, which we also don’t want to ship with the Charmcraft profiles  
* Add `SECURITY.md`  
  * Content: pointing people to the GitHub security reporting feature. Canonical charms would then swap in the Canonical-specific details  
  * `SECURITY.md` is a public listing requirement  
* Add a minimal publishing workflow  
  * Content: running charmcraft directly using a secret in an environment  
  * The public listing requirement includes having a "publish to edge on merge to default branch" requirement, so we do expect every charm to have this  
* Mention why 12-factor profiles will not receive GitHub CI configuration  
  * Confirmed by the Platform Engineering team  
* Use a version range for dependencies in the ci group. Call `integration.yaml` from `ci.yaml`.
